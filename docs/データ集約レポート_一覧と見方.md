# データ集約レポート — 一覧と見方

アクティブブック内の **「データ集約レポート」** シートに、データ集約の一括実行・ステップ実行の過程で記録される行の意味と、列・詳細 JSON の読み方をまとめたものです。実装の基準は `svc/svc_data_agg_write.py`（シート名・ヘッダ・整形）および `svc/svc_data_agg.py` / `svc/svc_data_agg_pipeline.py`（記録内容）です。

---

## 1. シートについて

| 項目 | 内容 |
|------|------|
| シート名 | **データ集約レポート**（既定）。旧名 **DataAgg_EventLog** のシートだけが存在する場合、実行時に新名へのリネームが試みられます。 |
| 同名シートが既にある場合 | **データ集約レポート_2** のように番号付きの別名になることがあります。 |
| シートが無い場合 | 初回の追記時にシートが追加され、1 行目に列見出しが書き込まれます。 |
| 追記方向 | 既存データの**下**に行が追加されます（時系列が下に伸びるイメージ）。 |

---

## 2. 列の意味（1 行＝1 イベントまたは 1 サマリ）

| 列名 | 意味 | 見方のポイント |
|------|------|----------------|
| **記録日時** | その行を生成したローカル時刻 | `YYYY-MM-DD HH:MM:SS` 形式。 |
| **区分** | 行の種類（日本語ラベルまたは理由コード） | 下記「区分一覧」のとおり。コードがマッピングに無い場合は**英字のまま**表示されます。 |
| **書込み方式** | Excel タブの**出力先**と**書込み方式**の要約 | 例: `アクティブシート / 追加`。**一括実行サマリ**行に主に入ります。パス追跡・結合イベントなどでは空欄のことがあります。 |
| **出力シート名** | 集約結果を書き込んだシート名 | **一括実行サマリ**で実際に出力したシートの名前。失敗で未出力の場合は空欄のことがあります。 |
| **シナリオID** | シナリオ JSON の `id`（無ければファイル名の stem 等にフォールバック） | どのシナリオの実行かを識別します。 |
| **対象パス** | ファイルパス **または** シナリオファイルパス | **結合イベント・パス追跡**では処理対象となった**データファイル**のパス。**一括実行サマリ**では**シナリオ JSON のパス**が入ります。 |
| **詳細** | 構造化情報（JSON 文字列） | セル内は 1 本の JSON。メモ帳やエディタに貼り付けて整形すると読みやすいです。Excel では列幅を広げるか、セル内改行を有効にして確認します。 |

---

## 3. 区分一覧（シートに出力され得るもの）

区分列は `_event_log_reason_ja`（`svc_data_agg_write.py`）で英字コードから日本語へ変換されます。未定義コードは変換されずそのまま表示されます。

| 区分（表示） | 内部コード | いつ出るか | 意味 |
|--------------|------------|------------|------|
| 一括実行・完了 | `BATCH_OK` | 一括実行が最後まで完了したとき | その実行の件数・処理時間などのサマリ。 |
| 一括実行・失敗 | `BATCH_FAIL` | 一括実行が途中で失敗したとき、または検証エラーで中断したとき | サマリ JSON の **エラー** に理由が入ることがあります。 |
| パス追跡（名前取得・実行前） | `PATH_TRACE_PRE_NAME` | パス追跡が有効で、名前取得ロジックの**適用前** | マージ済み行のスナップショット（パス列まわり）。 |
| パス追跡（名前取得・実行後） | `PATH_TRACE_POST_NAME` | 同上、**適用後** | 名前・パス反映後のスナップショット。 |
| （英字のまま等） | `JOIN_MISS` | 項目横結合（照合キー）で、左側のキーに対応する右側項目の行が無いとき | どのキー値で、どの項目 ID が欠けたか。 |
| （英字のまま等） | `JOIN_FAIL` | Polars による `join` が例外で失敗したとき | 例外メッセージと結合しようとした左右の項目 ID。 |

**補足（JOIN の区分）:** 現行実装では `JOIN_MISS` / `JOIN_FAIL` は `_event_log_reason_ja` の辞書に含まれていないため、**区分列は `JOIN_MISS` / `JOIN_FAIL` の英字**のまま出る場合があります。意味は上表のとおりです。

## 4. 詳細 JSON の形（種別ごと）

### 4.1 一括実行サマリ（`BATCH_OK` / `BATCH_FAIL`）

`種別` が **一括実行サマリ** のオブジェクトです。

| JSON キー | 意味 |
|-----------|------|
| `種別` | 固定で `一括実行サマリ`。 |
| `結果` | `成功` または `失敗`。 |
| `ファイル数` | スキャンして処理したファイル数。 |
| `出力行数` | マスタへ出力した行数。 |
| `追加行数` | 追記モード等で増えた行数。 |
| `更新行数` | 既存行の更新として数えた行数。 |
| `結合イベント数` | 結合まわりで記録したイベント件数の合計（ログ行数の目安）。 |
| `集計処理ミリ秒` | 任意。集計フェーズの処理時間。 |
| `書込ミリ秒` | 任意。Excel 書き込みにかかった時間。 |
| `合計ミリ秒` | 任意。実行全体の時間。 |
| `エラー` | **失敗時のみ**あり得る。シナリオ読込失敗・検証エラー・例外メッセージなどが文字列で入ります。 |

**見方:** まず `結果` と `エラー` を見ると、成功／失敗の理由が把握しやすいです。パフォーマンス調査では `*_ミリ秒` を参照します。

---

### 4.2 パス追跡（`PATH_TRACE_PRE_NAME` / `PATH_TRACE_POST_NAME`）

詳細は 1 つの JSON オブジェクトで、`種別` が **パス追跡** です。

| JSON キー | 意味 |
|-----------|------|
| `種別` | 固定で `パス追跡`。 |
| `パス列` | 名前取得の対象としている列名（ヘッダ名）。 |
| `列見出し` | スナップショットに含める列名の一覧（先頭付近の列が中心）。 |
| `行スナップショット` | 行ごとの辞書の配列。先頭から最大 **N** 行（N は設定・シナリオの `path_trace.max_rows_per_file` および設定 `PATH_TRACE.MAX_ROWS_PER_FILE` で上限あり）。 |

行オブジェクトに現れやすいキー（実装 `_snapshot_rows_for_path_trace` より）:

| キー | 意味 |
|------|------|
| `__path_ref__{列名}` | パス参照用の内部キー。 |
| 上記の `{列名}` | 実際のパス列のセル値。 |
| `__norm_path` | 正規化後のパス文字列。 |
| `__file_path` | 元ファイルのパス。 |
| `__iter_index` | ファイル内での行インデックス。 |
| その他 | 先頭から最大 12 列程度のヘッダ名がそのままキーになることがあります。 |

**見方:** 同一ファイル・同一シナリオで **実行前** と **実行後** の 2 行を並べて比較すると、名前取得でパスや関連列がどう変わったかを追えます。

**有効化:** シナリオ JSON の `path_trace.enabled` が真、または設定 `config/ui_data_agg.json` 付近の `PATH_TRACE.ENABLED` が真のとき（シナリオ側が優先）。

---

### 4.3 結合イベント（`JOIN_MISS` / `JOIN_FAIL`）

詳細列は **パイプラインが付けたイベント辞書を JSON 化したもの**そのままです（`format_join_events_for_event_log`）。

#### `JOIN_MISS`（キー不一致・右側に行が無い）

| JSON キー | 意味 |
|-----------|------|
| `reason_code` | `JOIN_MISS`。 |
| `match_keys` | 照合キー列名 → その行の値。 |
| `missing_item` | 一致する行が見つからなかった**項目 ID**（右側相当）。 |

**見方:** どのキーの組み合わせで、どの項目のデータが欠けたかを特定します。マスタに空欄や欠損が出る原因調査に使います。

#### `JOIN_FAIL`（結合処理の例外）

| JSON キー | 意味 |
|-----------|------|
| `reason_code` | `JOIN_FAIL`。 |
| `detail` | 例外メッセージ（ライブラリや型のエラーなど）。 |
| `left_item` | 結合の基準となった先頭項目の ID。 |
| `right_item` | 結合しようとして失敗した側の項目 ID。 |

**見方:** `detail` を手がかりに、列名の重複・型の不一致・Polars の join 制約などを調べます。

**出る条件:** シナリオに **照合キー（match_keys）** が定義され、複数項目を横方向に結合する経路を通る一括／ステップ実行時。ステップ実行は実装上一項目に絞るため、通常は **match_keys が空** でこの種の行は増えにくいです。

---

## 5. 記録の流れ（参照用）

- **一括実行:** 各ファイル処理中にパス追跡行・結合イベント行が `event_log_rows` に溜まり、成功／失敗の最後に **一括実行サマリ** が 1 行追加され、まとめてシートへ追記される経路と、早期失敗時に **サマリのみ** を先に追記する経路があります。
- **ステップ実行:** 同じ `compute_batch_table_rows` により `event_log_rows` が生成され、空でなければシートへ追記されます。

---

## 6. シートに出ないがデバッグ画面で見ることがあるコード

マスタデバッグ UI などでは、ログ表示用に **`NO_FILE`**（検出ファイル 0 件）などの合成イベントが使われることがあります。これらは **必ずしも「データ集約レポート」シートには書き込まれません**。シートに出た行は、原則として第 3 節の区分（および未定義の英字コード）に限られます。
