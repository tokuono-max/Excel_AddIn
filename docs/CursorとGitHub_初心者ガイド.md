# Cursor で GitHub を使う（初心者向けガイド）

本書は **Cursor（VS Code 系エディタ）** と **Git / GitHub** を組み合わせて開発する際の **考え方・準備・設定・操作** を、短い実例つきで整理する。コマンドに慣れていなくても、GUI から進められる流れを優先して書く。

> **用語**: 本文では「Cursor」と表記する（表記ゆれの「Cutsor」は Cursor の誤記として読み替えてよい）。

---

## 1. まず押さえる考え方

### 1.1 Git と GitHub は別物

| もの | 役割 | たとえ |
|------|------|--------|
| **Git** | PC 上で「変更の履歴」を記録する仕組み | 自分のノートに日付つきでメモを残す |
| **GitHub** | その履歴をインターネット上に置き、共有・共同作業する場所 | クラウド上の共有フォルダ＋掲示板（Issues / PR） |

Cursor は **Git を操作する UI** と **ファイル編集・AI アシスト** をまとめて提供する。GitHub 自体はブラウザや `git` コマンド経由で「リモート」に接続する。

### 1.2 日常の心構え（チーム開発で特に重要）

- **小さくコミットする**: 1 コミット＝「ひとまとまりの意図」（例: 「ログ出力を追加」「バグ修正」）。巨大な一括コミットは後から追いにくい。
- **push する前に差分を見る**: 意図しないファイル（`.env`、巨大ログ、venv 全体など）が混ざっていないか確認する。
- **main（または master）は安定版のイメージ**: 実験や大きめの変更は **ブランチ** を切ると安全。
- **Pull Request（PR）で合流**: レビュー文化があるチームでは、「直接 main に push」より **ブランチ → PR → マージ** が一般的。

### 1.3 Cursor における位置づけ

- **ソース管理（サイドバーの枝分かれアイコン）**: `add` / `commit` / `push` / `pull` / ブランチ切替などの起点。
- **ターミナル**: `git` コマンドと完全に同じ操作ができる（慣れたらこちらが速いことも多い）。
- **AI（チャット・エージェント）**: コード提案や説明に使う。**機密・トークンをチャットに貼らない**（後述）。

## 2. 環境整備（初回だけ）

### 2.1 必要なもの

1. **GitHub アカウント**（[github.com](https://github.com)）
2. PC に **Git**（Windows なら [Git for Windows](https://git-scm.com/download/win)）
3. **Cursor** 本体

インストール後、ターミナルで次を確認する。

```text
git --version
```

### 2.2 初回の Git 設定（ユーザー名・メール）

コミット作者情報として使われる。GitHub のプロフィールのメールと揃えると管理しやすい（公開したくない場合は GitHub の非公開メールを使う）。

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
```

確認:

```bash
git config --global --list
```

### 2.3 GitHub への認証（HTTPS と SSH）

リモートに `push` するには認証が必要。

| 方式 | 特徴 |
|------|------|
| **HTTPS** | URL が `https://github.com/...`。Windows では **Git Credential Manager** が案内され、ブラウザログインしやすい。 |
| **SSH** | URL が `git@github.com:...`。鍵を一度登録すると、パスワード入力が減る。複数 PC では各 PC に鍵。 |

**初心者向けの現実的な選択**: まず **HTTPS + Credential Manager** で始め、慣れたら SSH に移行、でもよい。

### 2.4 リポジトリを手元に持ってくる（clone の実例）

GitHub 上のリポジトリページの **Code** から HTTPS または SSH の URL をコピーし、手元の作業フォルダで:

```bash
git clone https://github.com/OWNER/REPO.git
cd REPO
```

その後 **Cursor で `File` → `Open Folder`** として、クローンしたフォルダを開く。

## 3. Cursor 側の設定・画面の見方

### 3.1 ソース管理ビュー

- 左サイドバーの **ソース管理アイコン**（分岐マーク）を開く。
- 変更されたファイルは **変更（Changes）** に並ぶ。
- **`+`（ステージ）** で「次のコミットに含める」対象にする。全部まとめてステージしたい場合は **「変更」行の `+`** やメニューから **Stage All**。

**実例**:

1. `README.md` を1行編集 → ソース管理に `README.md` が出る  
2. `README.md` の `+` でステージ  
3. メッセージ欄に `docs: README にセットアップ手順を追記` と書いて **Commit**  
4. **Sync / Push**（表示はバージョンにより「…」メニュー内）で GitHub に送る  

初回 `push` で **upstream が未設定**のときは、Cursor の案内またはターミナルで次のように設定することがある（ブランチ名は環境により `main`）:

```bash
git push -u origin main
```

### 3.2 ブランチ操作

- 画面左下の **ブランチ名** をクリック → 既存ブランチの切替や新規ブランチ作成。
- **実例（機能開発）**: `main` から `feature/add-export-csv` を作成 → そこで作業 → 完了後に PR。

### 3.3 差分（Diff）の確認

- ソース管理からファイルを開くと **変更前後** が並ぶ。AI に任せる前に、**自分の意図と一致しているか** を見る習慣をつける。

### 3.4 エディタ設定（任意）

Cursor は VS Code 互換の設定を持つ。**設定 UI**（`Ctrl + ,`）で例えば次を調べるとよい。

- `git.enabled` — Git 連携のオンオフ  
- `git.autofetch` — 定期的にリモートの更新を取りに行くか  
- `git.confirmSync` — `sync` 前に確認するか  

プロジェクトや個人の好みに合わせてよい。**初心者はデフォルトのまま**でも支障は少ない。

### 3.5 GitHub 公式拡張（任意）

VS Code マーケットプレイス由来の **GitHub Pull Requests and Issues** などを入れると、PR 一覧やレビューをエディタに寄せられる。必須ではなく、**ブラウザで GitHub を開く**運用でも十分なチームは多い。

## 4. 典型的な使い方（シナリオ実例）

### 4.1 実例 A — バグ修正を 1 人で main に載せる（小規模・個人）

1. `git pull`（または Cursor の Pull）で最新化  
2. コードを修正  
3. ソース管理でステージ → コミット（メッセージ例: `fix: 空行のみの CSV で落ちる問題を修正`）  
4. `push`  

**注意**: 共同リポジトリでは main 直 push が禁止されていることがある。その場合は **実例 B**。

### 4.2 実例 B — ブランチを切って PR 経由でマージ（チームありき）

1. `main` を最新化: `git pull origin main`  
2. 新ブランチ: `feature/ribbon-label`  
3. 実装・ローカルテスト  
4. コミット（必要なら複数回）  
5. `git push -u origin feature/ribbon-label`  
6. GitHub で **Compare & pull request** → 説明・レビュア指定 → マージ  
7. 手元の `main` を更新: `git checkout main` → `git pull`  
8. 不要ならローカルブランチ削除（任意）

### 4.3 実例 C — コンフリクトが出たとき（イメージ）

`git pull` や `merge` のとき **同じ行を双方が編集**していると、Git が自動マージできず **コンフリクト**になる。

1. Cursor が該当ファイルに **衝突マーカー**（`<<<<<<<` など）を表示する  
2. **どちらを採用するか／両方取り込むか** を人が決めて編集し、マーカーを消す  
3. ファイルを保存 → ステージ → コミット（マージ完了用のコミット）  

初めてのうちは、**バックアップを取ってから** `pull` する・変更を小さく保つ、と進めると心理的に楽。

## 5. このリポジトリ（Excel_AddIn）を想定した注意

本ワークスペースは **Python + venv + ビルド成果物** を含みやすい構成なので、GitHub に上げる前に次を意識する。

- **仮想環境（`.venv` など）** は通常コミットしない。リポジトリルートに **`.gitignore`** を置き、`venv` / `__pycache__` / `*.pyc` / 大きな `dist` などを除外する。  
- **認証情報・社内 URL・ライセンスキー** はリポジトリに入れない。環境変数やローカル設定ファイル（テンプレだけコミット）に分ける。  
- **生成物**（Nuitka や配布用 EXE の出力）をコミットするかはチーム方針次第。多くの場合は **CI で生成**し、リポジトリには載せない。

（既に `.gitignore` が無い場合は、テンプレートを追加するのが無難。）

## 6. Cursor × AI を使うときの GitHub 関連トピック

### 6.1 秘密情報をコミットしない

- `.env`、`credentials.json`、API キー、個人トークンを **コミットに混ぜない**。  
- AI チャットに **本番のトークン**を貼らない（ログや学習の取り扱いはサービス側ポリシーに依存する）。

### 6.2 `.cursor/rules` やプロジェクトドキュメント

チームで Cursor を使う場合、**コーディング規約やブランチ命名**を `.cursor/rules` や `docs` に書いておくと、AI の提案が揃いやすい。GitHub 上の「どこに何があるか」も README や `docs` 索引があると新人が迷いにくい。

### 6.3 大きなファイル

Git は巨大バイナリに弱い。**Git LFS**（Large File Storage）を使うか、別ストレージに置くかはチームで決める。誤ってコミットした場合は履歴からの除去が面倒になるので、**早めに `.gitignore`** が効く状態がよい。

### 6.4 Issue / PR と仕様書のリンク

実例: Issue `#123` の修正なら、コミットメッセージや PR 説明に `Fixes #123` と書くと、GitHub が自動で紐づけたりクローズしたりする（リポジトリ設定による）。

## 7. コマンド早見（GUI と対応させる）

| やりたいこと | コマンド例 |
|--------------|------------|
| 状態確認 | `git status` |
| 差分 | `git diff` |
| リモートから取得＋統合 | `git pull` |
| コミット履歴 | `git log --oneline -10` |
| ブランチ作成＋切替 | `git checkout -b feature/foo` |
| リモートに送る | `git push -u origin feature/foo` |

Cursor のボタンは、裏でこれらと同じ処理をしていることが多い。**困ったらターミナルで `git status`** が最速の診断になりやすい。

## 8. トラブル時の第一歩

1. **`git status`** — 今どのブランチで、何がステージされているか  
2. **リモートに自分の push 権限があるか** — 組織のリポジトリでは権限不足がよくある  
3. **認証エラー** — HTTPS のトークン期限切れ、SSH の鍵・`ssh -T git@github.com` の確認  
4. **間違えてコミットした** — まだ push していないなら `git reset` 系で戻せることがある（**共有ブランチでは慎重に**）  

詳細は状況依存が大きいので、エラーメッセージ全文を検索するか、チームの開発ドキュメントを参照する。

---

## 9. まとめ

- **Git＝履歴、GitHub＝共有と共同作業の場、Cursor＝編集と Git 操作の窓口** と捉えると迷いにくい。  
- 初回は **clone → ブランチ → 小さくコミット → push / PR** の型を身につける。  
- **秘密情報・巨大生成物・venv** はリポジトリに入れない前提で `.gitignore` と運用ルールを整える。  

このファイル自体も Git 管理下であれば、改善したら **コミットして PR** に載せると、後から来た人にも同じ手順が伝わる。
